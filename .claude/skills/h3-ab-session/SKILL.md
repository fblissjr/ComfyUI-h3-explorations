# A rendered comparison in this repo

Read `docs/eval_comparison.md`, section 3, and follow it. That file owns the
process; this skill only makes sure it is reached.

The four pieces, in order, each a `bench/` script with its own docstring:

1. `bench/run_graph_arms.py` -- renders the arms, alternating, with a seed base
   and `--runs N`, and records the substrate per row.
2. `bench/blind_batch.py` -- neutral clips plus a sealed key under
   `internal/blind_keys/`; `--pairs A,B` for a two-arm session; writes the
   scoring app into the batch directory.
3. The owner scores in `score.html` (generated by `bench/blind_score_app.py`)
   and exports `scores_<session>.json`.
4. `bench/score_session.py` -- the only place the key is opened -- writes
   `bench/results/<date>_<session>_verdict.json`.

Three rules that are not the process's to relax, all from `CLAUDE.md`:

- A rendered clip cannot A/B a numerical knob: two arms are two samples, so a
  claim needs many seeds judged blind in aggregate, and a single pair is a
  presentation, never a result.
- The key is not opened until the scores exist. Nothing the judge sees carries
  an arm label, including filenames and terminal output.
- The output share's path comes from `H3_COMFY_OUTPUT` (or `folder_paths` on
  a live server) and is typed in the shell, never written into the repo.

If a step here disagrees with `docs/eval_comparison.md`, that doc is right and
this file is stale.
