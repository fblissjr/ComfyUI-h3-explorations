## The trap that cost the most, and the rule that came out of it

**A render is not a pure function of its graph.** ComfyUI's execution cache
persists across prompts in a session, keyed by input signature. Two graphs
differing in one widget share every cached node upstream of it.

That produced the session's most confusing result: `C_pdd8` at two seeds, one
OOM and one success on identical graphs. It was read as nondeterminism for an
hour. The first ran after a restart and paid the whole model load; the second
hit cache on the encoder, the conditioning and the loader.

**So any arm whose outcome is TIME or MEMORY must state what ran before it.**
Output is unaffected, so perceptual comparisons are safe.
`bench/record_render_substrate.py` records position-in-session and cache
fraction per render; run it before quoting any duration.

It also recovered a measurement on its first run: selecting rows at matched
cache fraction gives `start_percent` 0.0 against 0.2 at **11.4%** faster --
the first time that knob has been measured at any value.

## The AWQ loader diverges from ComfyUI in one way that reaches published users

Traced 2026-08-27 late, both encoder paths end to end, after the owner asked
whether the adapter composes the way core's `CLIPLoader` does.

**The memory hypothesis is dead, with a mechanism.** Both paths converge on
`comfy.sd.load_text_encoder_state_dicts`, so the `ModelPatcher`, `model_size`,
device selection and offload are core's own code in both. The adapter makes
zero `comfy.model_management` calls. And VRAM is not released by refcount --
unloading goes through `LoadedModel.model_unload` and `get_free_memory` reads
device counters -- so no Python reference the adapter holds can make ComfyUI's
free-VRAM figure wrong. That closes the "keeping something alive" line.

**VERIFIED, and it is live for everyone running the published loader:**

    adapter  h3_awq_encoder.py:499  mixed_precision_ops(compute_dtype=torch.bfloat16,
                                                        full_precision_mm=False)
    core     comfy/sd1_clip.py:114  mixed_precision_ops(quant_config, dtype,
                                                        full_precision_mm=True)

Core threads `dtype` from `text_encoder_dtype(load_device)`; the adapter
hardcodes it. **So `--fp32-text-enc`, `--fp16-text-enc` and the `--fp8-*-text-enc`
flags are silently ignored** -- a user asking for fp32 gets bf16 and no warning.
Read from both call sites, not run. It does not corrupt accounting, which
measures the tensors that exist.

**The monkeypatch violates this repo's own stated rule.**
`h3_awq_encoder.py:780` assigns `preprocess_embed` directly onto
`cond_stage_model`, where `conditioning.py:36-40` refuses to do exactly that on
the ground that `CLIP.clone()` shares by reference so a patch leaks into every
other graph in the process; `marker_arms.py` and `bench/check_marker_arms.py`
encode the same rule. It is not in `object_patches`, so `unpatch_model` never
reverts it. Core's convention would be
`clip.patcher.add_object_patch("transformer.preprocess_embed", ...)`.

Two smaller ones: the adapter writes `h3_awq_w4a16` into `comfy.ops.QUANT_ALGOS`
process-wide at load and never removes it; and `full_precision_mm=False` against
core's `True`, where the adapter is the leaner of the two.

**What this means for the HF repo.** The dtype bug is the only one of these that
reaches published users and the only thing found tonight that would justify a
push -- unlike the menu default, which is structurally unreachable in the
standalone. The `code/` directory and the quantization report are also
unpublished, so the artifact ships without the means to reproduce or check it.

**A correction worth keeping:** `bench/check_lowvram_handoff.py` is NOT evidence
about `--lowvram` in either encoder path. It grades the DiT attention forward
against KJNodes' block patch. Same vocabulary, different model -- the trap
CLAUDE.md names.

## One open lead on the OOM, measured but not resolved

Observed 2026-08-27 late, mid-batch, with a render in flight:

    ComfyUI /system_stats   vram_free 18,613 MiB   torch_free 15,277 MiB
    nvidia-smi              20,766 of 24,564 used -> ~3,798 MiB actually free

**ComfyUI believes roughly 18.6 GiB is free where the card has 3.8 GiB.** If
its offload and fit decisions run off that figure they are being made against
something about five times too optimistic, which is the right shape for an OOM
on a configuration that ought to fit.

**Not a finding.** There is a mundane competing explanation that cannot be
ruled out from outside the process: torch's caching allocator holds RESERVED
memory that `nvidia-smi` counts as used and torch counts as free. If the gap is
reserve pool, ComfyUI's number is legitimate and nothing is wrong.

**The measurement that decides it**, from inside the process:
`torch.cuda.memory_reserved()` against `torch.cuda.memory_allocated()` at the
same moment. Reserved accounting for the gap means the allocator, and the lead
dies. Allocated high with reserved not accounting for it means something is
resident that ComfyUI is not counting.

Two documented AWQ-path behaviours are related and worth checking against the
INT8 path we moved to, since if either has an analogue the trap moved with us:
`docs/h3_awq_encoder.md` records that above `M > 256` tokens the kernel
**dequantizes the whole weight matrix to BF16**, and that image and video
references can produce enough visual tokens to enter that route; and that
retained vision tensors keep their source BF16 rather than being quantized.
