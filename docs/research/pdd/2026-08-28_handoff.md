## 0. Read this first if you read nothing else

Three things this session got wrong and then corrected. If you find yourself
about to conclude any of them, you are repeating work:

1. **"4-step PDD is our own extrapolation."** It probably is not — see §1. This

## 1. The paper changes the lane's central conclusion

The paper is saved at
[`arxiv_2607.26004v1_Parallel_Decoding_Distillationfor_Fast_Image_and_Video_Generation.md`](arxiv_2607.26004v1_Parallel_Decoding_Distillationfor_Fast_Image_and_Video_Generation.md).
Line numbers below are that file's.

### Variable NFE is the designed feature, not a deviation

| where | what it says |
|---|---|
| line 23 (abstract) | *"By varying the block size during training, PDD supports sampling with different number of function evaluations (NFEs) during inference."* |
| line 308 (Table 1) | PDD's NFE row reads **Variable**; Pi-Flow's reads *Fixed* |
| line 342 (§5) | `L_min` and `L_max` *"determine the set of available NFEs at inference time"* |
| line 352 (§5) | available NFEs are *"2,4,8 for Qwen-Image and Wan2.1, and **4,8** for LTX-2.3"* |

**LTX-2.3 is the row that matters.** It is the 22B joint **video+audio** model —
the only multimodal case in the paper and the closest analogue to H3. Its
trained NFE set is {4, 8}.

### What that implies for the H3 artifacts

The released files declare (read from the safetensors `__metadata__`):

    pdd_num_steps    32
    pdd_block_size    4
    pdd_nfe           8
    pdd_shift_video  12.0
    pdd_shift_audio   3.0

`32 / 4 = 8`. If `L_min = 4` and `L_max = 8`, the available NFEs are **{4, 8}** —
the same set the paper chose for its multimodal model. So **4 evaluations is
most likely a trained configuration for these files.**

### 2.2 The six-evaluation arm — the best untried thing in the lane

**Source:** paper line 282, §3: *"during training, we consider multiples of
`L_min` for indices `n` of initial states and sample `k` in
`{n, ..., n + L_max - 1}` inside each block."*

So a legal partition needs **every block to start at a multiple of `L_min`** and
**no block wider than `L_max`**. With 4/8 the block sizes compose from `{4, 8}`,
and at six evaluations `4+4+4+4+8+8 = 32` satisfies both.

`resolve_emit_steps` (in `pdd_lora.py`) **refuses 6**, because the SIGMAS output
requires a count that divides the grid uniformly. The run-time path does not:
`pdd_math.schedule_knots` takes an uneven partition and the node reports it. So
the arm is reachable **today, with no code change**:

    ManualSigmas -> "1.0, 0.988235, 0.972973, 0.952381, 0.923077, 0.8, 0.0"
    knots [0, 4, 8, 12, 16, 24, 32]   widths [4, 4, 4, 4, 8, 8]

**How to run it:** add it as an arm in `bench/grade_pdd_partitions.py`, which
already grades against the 32-step reference and has a zero noise floor. Do not
hand-roll a comparison.

**Predict before running** (the repo's own rule): landing between u8 (0.458) and
u4 (0.531) on video means a 6-step schedule is doing what it should. Landing
worse than u4 means uniformity matters more than the paper's rule implies.

**Follow-on only if it works:** `resolve_emit_steps` should accept an explicit
non-uniform knot list rather than only divisors. Do **not** build that first.

**Reported by a peer session, not verified here:** `Comfy-Org/ComfyUI#15908`
changed its head formula after commit `bd016b75ff9b` to one correct only if the
stored rows are **deltas from head 0**; our local copies are verbatim heads; and
the HF repo's `lastModified` sits two minutes after that commit, so upstream may
have re-uploaded.

**Verified here:** our source files are byte-identical to what the 2026-08-27
record hashed (`sha256` unchanged), and the bank rows are verbatim — row-norm
ratio **0.9906**, every row within ~1% of every other. A delta encoding would
put rows 1..31 far below row 0.

**The hazard, and it is real:** `bench/convert_pdd_lora.py` copies
`proj_out.weight` into `h3_pdd.bank.*` **verbatim, with no encoding check**.
Re-fetch a delta-encoded artifact and the converter silently produces a wrong

checkpoint's* head, not the bank, and `compare_pdd_conversions.py` compares our
bank against the same source file it came from.

**Order of operations:**

1. Add the row-norm detector to the converter. Refuse or branch on the
   observable; do not guess. Give it a deliberate-violation proof.
2. **Then** re-fetch, into a **dated** directory, leaving the current symlinked
   copies in `coderef/alibaba-pai_MiniMax-H3-Acc-LoRAs/` untouched.
3. Re-run `bench/compare_pdd_conversions.py` against both.

### 2.5b The euler gap is structural — do not try to close it with tolerance

**Verified here** by driving the real `_StepTracker` with a real
`adaln_t_table` over heun's evaluation pattern; reported first by a peer.

`comfy/k_diffusion/sampling.py:296` evaluates heun's corrector at
`sigmas[i + 1]` — which **is** the next block boundary. `BOUNDARY_TOLERANCE`
measures distance to the nearest boundary, so it sees ~0, which is exactly the
state it calls healthy. At 4 steps, knots `[0, 8, 16, 24, 32]`:

    step  evaluation          sigma   block   warned
       0  euler predictor   1.00000       0    False
       0  HEUN corrector    0.97297       8    False
       1  euler predictor   0.97297       8    False
       1  HEUN corrector    0.92308      16    False

Every corrector selects the **next** block's head while integrating the current
step, and `warned` never flips. `er_sde` is invisible the same way.

**If you close it, the observable is the number of model calls per step or the
sampler's identity — never the distance to a boundary.** Tightening the
tolerance cannot reach this and will waste your time.

### 2.6 `sampler_name` — deliberately not built

`docs/h3_pdd.md` calls euler a **requirement**, not a preference: a fused head
is the block's mean velocity, and anything that re-noises between boundaries is
answering a question the sampler did not ask. There are 44 `sampler_name`
options and ~20 dedicated SAMPLER nodes, nearly all invalid here.

**Enforced by nothing.** No check reads `sampler_name` off a graph, and unlike
the shift, the node **cannot** see the sampler — `KSamplerSelect` is not in
`transformer_options`, so the run-time trick used for the shift guard is not
available.

**Not built on purpose**, per this repo's rule of no new check without an
escaped instance: every shipped graph carries euler. Recorded so the first time
a non-euler PDD graph appears, the justification is ready.

### Why the SIGMAS rewiring exists

Every knob that could put a distilled render off its grid — `scheduler`,
`steps` — lived on `BasicScheduler`, which sits **downstream** of every
model-patch node. So the PDD node could only ever observe the schedule after the
fact and report. Three footguns followed, each caught (if at all) by a static
check over *shipped* graphs, leaving a hand-edited graph with nothing.

Emitting the schedule inverts the dependency: the sampler steps the boundaries
the heads were fused for, there is no scheduler widget to set wrong, and
off-grid is not expressible. `silveroxides/ComfyUI-UtilsCollection` reached the
same design from the other end; its off-grid error tells you to use its SIGMAS
output.

**Verified inert:** eight settled runs at 39 frames, four old-wiring and four
new, **pixel-identical**; same at a second step count. The closed form is also
bit-identical to `BasicScheduler(simple, N)` at 2, 4 and 8 steps on shift 12 and
shift 6. At 16 they differ by ~2e-3 because `1000 % 16 != 0` and `simple`
quantises against its table — the closed form is the more correct there, and no
PDD graph runs 16.

### 4.2 The refuted prediction, and why the paper explains it

A DP over all 528 spans found `[28,2,1,1]` minimises the worst per-block
fusion loss by 2.95× at four evaluations. **Measured, it is further from the
trajectory than uniform** (0.552 vs 0.531).

Paper line 282 gives the mechanism: training takes block starts at multiples of
`L_min` and offsets below `L_max`. `[28,2,1,1]` starts two of four blocks
off-multiple (30, 31) and makes one 28 wide — **outside the training
distribution in a way fusion loss structurally cannot see**, because it reads
head weights and knows nothing about which spans were trained.

Worth keeping: the arc-length observation still stands. Under shift 12 the
uniform partition spends one Euler step on **80%** of the trajectory
(2.7 / 5.0 / 12.3 / 80.0 %). It just does not follow that rebalancing helps.

Both partitions re-converted from identical inputs: **all 730 tensors
bit-identical, every metadata value identical, file sha256 differs.** The only

**So a converted artifact's file hash is not a stable identity**, and

## 5. Methodology traps — every one of these cost time this session

1. **Compare decoded pixels, never file bytes.** `SaveImage` embeds the prompt
   JSON, so arms differing only in `filename_prefix` produce different files
   with identical frames. This produced a false "the rewiring broke something"
   for several minutes. `docs/h3_pdd.md` already recorded the same trap for mp4
   containers one day earlier.
2. **A render has a warm-up transient.** The first render or two after a state
   change differ from what that configuration settles on, and it hits **both**
   wirings equally. Against a single matched pair it reads exactly like a
   regression. Only interleaved repeats separate them. The settled state *is*
   deterministic — noise floor exactly 0.
3. **A raised render contaminates the next one in the same session.** A warning
   fired on a graph queued after a `RuntimeError` render, and did not fire on
   the same graph in a clean session.
4. **`denoise < 1.0` needs no fallback.** `SIGMAS(8) → SplitSigmasDenoise(0.5) →
   low_sigmas` is `torch.equal` to `BasicScheduler(simple, 4, denoise=0.5)` and
   renders pixel-identically — and is *better*, because every entry of the
   emitted vector is a block boundary, so an index split lands on-grid by
   construction.
5. **Fix one path, break another.** The smoke's `--steps` had been dead on PDD
   graphs; making it live sent the default of 10 into `resolve_emit_steps`,
   which raises, killing the default smoke. **After a fix, ask which code paths
   were dead before and are live after** — they are unexercised by construction
   and no existing test covers them.

## 6. The rule that came out of the reviews

**A check that RESTATES the expression it grades cannot fail when the expression
is wrong** — it grades its own copy. Written up in `docs/checks.md` under "The
standard", with both escaped instances.

It escaped twice in one lane in one day. `check_pdd_sigmas::emitted()`
recomputed `1 - block_bounds(...)`, and dropping the `1.0 -` in `pdd_lora.py`
left **every case in that file green**. Fix: lift the expression to a module
function and have the check call it — `emit_sigmas` and `resolve_emit_steps`
exist for no other reason.

**The tell for a reader:** if you can delete the implementation and the check
still passes because it computed the answer itself, it is not a check.
