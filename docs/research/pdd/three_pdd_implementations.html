Three PDD Implementations

A third pack implements the same mechanism, converts the published file in the node, and hands the sampler its own schedule. On guards it is ahead of both of the others.

It is a PDD implementation

The question was open — ComfyUI-UtilsCollection is a general utility pack and the two files named could have been generic patcher plumbing. They are not. patcher_nodes.py declares UC_MiniMaxH3PDDAcc, and patcher_helpers.py carries a complete PDD path: grid arithmetic, an in-node converter for the published alibaba-pai layout, head fusion, an AdaLN rebase for pruned checkpoints, block selection, and the patch installation.

So all three are directly comparable, and the pack overlaps ours on every axis rather than on some of them.

Ours

MiniMaxH3PDDLoRA

Offline converter writes a file with h3_pdd.* sidecar tensors; the node reads it, fuses heads at load, and swaps the two output linears per step.

Kijai

stock loader + Comfy-Org/ComfyUI#15908

The bank rides in an ordinary LoRA file through core's generic reshape_weight adapter; a core patch to FinalLayer.forward blends the spanned heads per forward.

Where the block index comes from

All three answer the same question every sampling step: which fused head does this step want. They get there from different places, and the number of things a person has to keep in agreement differs with it.

Ours and the third pack both recover the step from what the model was actually called with, so both survive a step cache or a two-pass split; Kijai's argmin against the schedule does not. The difference between ours and theirs is upstream of that: we ask the user for nfe because the node runs before the scheduler exists, and they removed the question by making the node the scheduler.

Moving as this was written

The top lane describes MiniMaxH3PDDLoRA as it stood at the start of 2026-08-27. It is being changed the same day: the nfe widget goes away and the count is derived from the sampler's own schedule at runtime, which reaches the same one-source-of-truth property from the opposite direction — they emit the schedule, we read it. Treat the dashed warning arrow as the problem being solved, not as current state.

Which partitions of the grid are allowed

The trajectory is 32 intervals. A sampling step consumes a contiguous block of them. Ours accepts any block size that divides 32; theirs accepts only the trained block and double it, which is a claim about the distillation rather than about the arithmetic.

patcher_helpers.py, resolve_pdd_partition

allowed = (trained_block, 2 * trained_block)
invalid = sorted({size for size in sizes if size not in allowed})
if invalid:
    raise ValueError(f"partition {sizes} contains block sizes {invalid} "
                     f"outside the trained envelope {allowed}")
Open question for us

bench/check_pdd_head_selection.py drives and asserts nfe 16, 8, 4 and 2, on the grounds that every divisor lands exactly on its own shifted schedule. That is true of the arithmetic and says nothing about whether a block of 16 heads averaged into one velocity is anywhere near what the block-4 distillation trained. Their envelope says it is not. Neither position has been tested against a render.

Who owns the fused heads at runtime

All three end up doing F.linear against a per-block weight. They disagree about who is responsible for that tensor existing on the right device, which is the question ComfyUI's streaming loader turns into a trap.

Theirs is the better answer to the problem ours works around. Our closure keeps the tensors off the loader's books by making them invisible, at the cost of hand-rolling the device cache and getting no VRAM accounting. A standalone ModelPatcher attached with set_additional_models is managed by ComfyUI without going near the diffusion model's parameter tree, so the trap never applies — and the bank's project() raises if the tensors did not arrive on the expected device rather than silently transferring.

Every core API this depends on — set_additional_models, add_wrapper_with_key, remove_wrappers_with_key, WrappersMP.DIFFUSION_MODEL — exists in the ComfyUI installed here, so this path would run on this box.

The arithmetic agrees

Independently of the packaging, this is a third arrival at the transforms our converter performs, and it agrees on every one.

  • The four backbone transforms. q/k/v concatenated down, block-diagonal up, alpha * 3.0; attn.to_out.0 to attn.out_proj; ff.net.2 to mlp.fc2; and ff.net.0.proj to mlp.fc1 with the output halves swapped.
  • Explicit .alpha tensors, as ours writes and Kijai's files omit.
  • The affine AdaLN projection. diff = scale * (up @ (down @ basis)) and diff_b = scale * (up @ (down @ center)) — the basis plus a constant column, which is the same solve ours performs and the same one Kijai's pruned build reaches.
  • Per-stream fusion shifts. Video heads fused on the 12.0 grid, audio on 3.0, while block selection uses the video sigma alone — the grid position is shift-invariant, so one index serves both streams.

Three independent implementations now agree on the SwiGLU half-swap and the block-diagonal qkv fusion, which are the two easiest things here to get wrong.

One numerical nicety we do not have: pdd_fine_sigmas pins values[0] = 1.0 and values[-1] = 0.0 after shifting, so the endpoints are exact rather than whatever the rational shift returns.

What each does better

Ahead of ours

  • No offline conversion step. split_pdd_state_dict accepts the published alibaba-pai layout and converts in the node, or takes a pre-converted file. Ours requires running bench/convert_pdd_lora.py first.
  • The schedule is an output, not a second question. One place the step count exists. Ours is converging on the same property from the other side — deriving the count from the sampler rather than emitting it — which closes the gap but leaves theirs the simpler graph.
  • Failing closed. Off-grid sigma, partial key match, wrong head shape, wrong shift, unknown key, unmatched basis — all raise. Ours warns or ignores on most of these.
  • Separate lora_strength and head_strength, where ours has one knob scaling all three surfaces together.
  • Head custody through a real ModelPatcher rather than a hand-rolled cache.
  • Refusing to stack with another final-layer patch, or with its own Cache and Spectrum nodes.

Ahead of theirs

  • The partition fingerprint. Ours is still the only one of the three that notices a Ref2VA file on an fl2va checkpoint.
  • Delegating the modulation. Their pdd_final_forward re-implements the body of core's FinalLayer.forward and imports the private minimax_model._mod_row; ours does bookkeeping and calls the stock forward, so upstream cannot silently diverge from us.
  • Arity transparency against #15908, as of today.
  • A stable artifact. Converting offline gives a file that can be hashed, compared against other conversions, and shipped; theirs re-derives on every load.
  • Selection from t_emb including the per-token denoise-mask case, where theirs reads the scalar timestep.
Worth watching, not verified

Their basis match is torch.allclose(basis_table, table, atol=1e-6). Our own TABLE_TOLERANCE note records shipping 1e-3 for an hour and finding it below the 1.6e-3 a bf16 cast of that table costs — a tolerance under the noise it has to absorb, which rejects correct state. Theirs is three orders tighter still. Whether that bites depends on how the AdaLN table is stored and cast in the checkpoints they target, and nothing here has run it.
