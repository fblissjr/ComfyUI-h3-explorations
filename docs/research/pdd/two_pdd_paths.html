Two PDD Paths

Graph

One spine, four graphs, one slot that differs

Every PDD workflow in the repo is the same chain with one node swapped. Two facts in the drawing are load-bearing and easy to miss in prose: the accelerator sits upstream of the sigma shift and the attention nodes, and BasicScheduler hangs off the end of that chain — so the shift the sampler's sigmas are built from is the one the accelerator node has already seen.

Load time

Where the head bank goes

This is the divergence everything downstream inherits. Ours never touches the checkpoint's output projection: the fused heads live in a closure and are applied by an object patch. His replaces that projection outright, because ComfyUI's generic LoRA adapter is allowed to change a weight's shape — so after load his model's final_layer.video_out.weight is thirty-two times taller than ours.

Per step

Where the fusion happens

Both implementations end at the same operation — one F.linear against a step-appropriate head. They differ in when that head is built and in what the step index is derived from. Ours reads t_emb, the tensor the model was actually called with. His reads sample_sigmas, which has to be threaded in from outside the forward.

The grid

Thirty-two intervals, two step counts, one disagreement

The trajectory is always a 32-point grid. A step count that divides 32 subsamples it exactly, which is why a PDD arm moves the sampler's step count and nothing else — no shift change, no custom scheduler. Both implementations land on identical blocks there. They part company only when the step count does not divide 32.

The four graphs

What each one actually carries

Read off the graph files rather than from the generator. The two 8-step graphs carry nfe: 0, which the node resolves to the count the file was converted for — the file's pdd_nfe is 8. The Sol window narrows with the step count so the final step still runs dense, which is the one setting that changes between the 8- and 4-step arms for reasons that have nothing to do with PDD.

Divergence

Four places the two paths behave differently

None of these change the default render. The first three matter the moment someone moves off the default. The fourth would have mattered the moment the PR merged, and is now closed.

Strength below 1.0 means different things

off-default

Ours interpolates every head toward the checkpoint's own: base + s × (fused − base), so 0.0 is exactly the base model, heads included. His arrives through zero padding, so head 0 interpolates from the base but heads 1 through 31 scale from zero — at strength 0.5 the last block decodes with a half-magnitude head.

Worth knowing because sweeping strength is a natural first experiment, and on his path it does not degrade gracefully.

The partition fingerprint exists on one side only

silent failure

The fl2va and ref2va partitions ship identical key sets, so the wrong file loads with zero unmatched keys and renders. We store the checkpoint's own final_layer.video_out.weight as h3_pdd.base_video_out and refuse on a relative-distance mismatch. His metadata names no checkpoint and carries no fingerprint.

Alpha rests on a coincidence

latent

His files carry no .alpha tensors, so ComfyUI's adapter falls back to a scale of 1.0. That is correct here only because PDD's alpha / rank happens to be 1.0. Our converter writes the alpha tensors explicitly rather than depending on the fallback continuing to agree.

The forward signature collides

found, closed 2026-08-27

PR 15908 changes FinalLayer.forward to take seven arguments and updates the call site to match. Our object patch installed a four-argument replacement, so the first sampling step after a merge would have raised a TypeError — loud and immediate rather than a silently wrong render, but a hard break. Our two output-linear patches would have survived it, since core takes the n == 1 path when the weight has not been enlarged and still calls through video_out.forward.

Closed in commit 999e0c4. _make_final_layer_forward now binds (x, t_emb, video_seg, audio_seg, *args, **kwargs) and forwards the extras to base_forward verbatim; the tracker still reads only the first four.

bench/check_pdd_head_selection.py is what holds it closed — a third section asserting both signatures, today's four arguments and the seven the PR introduces, with the extras arriving unchanged. It needs no checkpoint, so it runs even when the rest of that check skips. Graded by deliberate violation: pinning the patch back to four parameters turns the second case red. That violation also exposed a defect in the case itself, a TypeError escaping past check()'s AssertionError handler and aborting the run instead of reporting a named failure, so the case now converts an arity mismatch into an assertion.

Reading

What the comparison comes down to

His is the better distribution story: one file, the stock loader, no custom node, and the mechanism upstream where everyone gets it. Ours is the better inference story: the fusion happens once instead of thirty-two times a render, the step index comes from an argument the model already has rather than state threaded in from the sampler, and the load path refuses a partition mismatch and an illegal step count instead of proceeding.

Those are not in tension. They are different bets about where the risk lives, and the arithmetic underneath them is the same to eleven decimal places.

One consequence for this repo, also closed today: bench/compare_pdd_conversions.py read his bank by the literal key diffusion_model.final_layer.video_out.set_weight, which his 2026-08-27 files no longer carry, so it died with a KeyError — the second-implementation cross-check had quietly become no check at all. It now branches on which keys are present, reconstructing through the documented adapter path where it must: a branch on the observable rather than on one implementation's spelling, which survives his next repackaging.
